#### 4.1.1 Quasi-Experimental Design

This study adopts a 12-week quasi-experimental design to compare Trade-Harness with a conventional prompt-based AI-assisted workflow during normal front-end development. Both conditions use Claude Code CLI with Claude Sonnet 4.6 in the same development environment. The comparison focuses on the workflows used to complete real development tasks, rather than differences between language models or coding tools.

The study is conducted in the front-end system of a cryptocurrency trading platform. The system contains approximately 722,000 lines of code and nearly 70 component libraries maintained by a team of 13 front-end developers. Changes to business logic, shared components, and dependencies may span multiple repositories, requiring developers to coordinate implementation and validation across the codebase. This provides an industrial setting in which to examine whether structured workflow orchestration is associated with different development outcomes.

A fully randomized experiment is not used because tasks must be allocated within the team's normal delivery process. The technical lead assigns work according to business domain, estimated effort, and developer availability. During the study, the two participating developers each use both workflows on different tasks. The technical lead aims to balance the allocation of the two workflow conditions within each developer and task-complexity category, although operational requirements may prevent an equal distribution. Tasks are classified using information available before development begins; the classification and assignment criteria are described in Section 4.1.2.

Each task is implemented once as part of normal project delivery. Repeating the same task under both workflows would not reflect ordinary practice and could favour the second attempt through knowledge gained during the first. Balancing tasks by developer and complexity helps make the conditions more comparable, but it does not remove differences in task requirements, developer familiarity, or other project circumstances. The findings are therefore interpreted as observed differences between the workflows within this setting, rather than as evidence that the workflow alone caused the outcomes. The overall execution procedure and remaining threats to validity are addressed in Sections 4.1.4 and 4.3, respectively.
