#### 2.3.2 Existing Approaches and Empirical Evidence

Retrieval addresses the problem of supplying relevant code or documentation at the point where the agent needs it. RepoCoder uses an earlier completion to refine subsequent retrieval and improves repository-level completion over an in-file baseline and a simpler retrieval approach (Zhang et al., 2023). De-Hallucinator applies a similar idea to project APIs. It uses a model prediction to identify relevant API references, improving API prediction for Python completion and correcting some JavaScript tests that initially failed with errors associated with hallucinated APIs (Eghbali & Pradel, 2024). These studies evaluate different outputs, but both use an initial candidate to guide the search for supporting information.

The relevance and coverage of retrieved material both affect what the model has available for generation. On CloudAPIBench, Jain et al. (2025) found that the mean valid invocation rate for StarCoder2-3B increased from 41.80% to 86.82% when the correct API specification was supplied through oracle retrieval. In a separate comparison on high-frequency APIs, adding one document at 50% retrieval precision reduced that subset's rate from 84.39% to 67.32%. Hai et al. (2025) examined a related problem on RepoExec and found that retaining full dependency context gave the best performance among their tested settings. Le-Anh et al. (2026) extended retrieval to external libraries and reported gains in functional correctness on repository code-generation benchmarks. Taken together, these results show why the scope of retrieval matters. A narrow selection can omit definitions needed to generate the code, while an imprecise retriever can supply information unrelated to the task. The library retrieval results provide a reason to consider dependencies outside the current repository, with direct evaluation still needed for dependencies among internal front-end repositories.

Handoff and memory approaches differ in what they carry forward. KC and Budathoki (2026) compared repository-only takeover with takeover supported by a raw trace, summary, or structured notes. Providing a handoff that included context reduced median agent events by 20–59% across the tested successor models, while effects on the proportion of tasks solved were smaller and varied by model. Shen et al. (2026) studied agents drawing on previous issues. Organising that experience by subtask improved mean Pass@1 on SWE-bench Verified by 4.7 percentage points over agents without memory, averaged across the tested models. The handoff experiment gives clearer evidence about the effort needed to resume an issue. The memory experiment gives evidence about issue resolution when prior experience can be retrieved for the appropriate stage. A third case is providing general repository guidance. Gloaguen et al. (2026) found that repository instruction files did not generally improve task success in their evaluation. The role of the information, whether task state, prior experience, or project guidance, therefore matters when interpreting what the study measures.

Compaction approaches differ in what triggers a summary and how much of the earlier context it replaces. In *Context as a Tool*, Liu et al. (2025) trained an agent to trigger context maintenance and retain task information in a structured workspace. Their system solved 57.6% of SWE-bench Verified issues and outperformed the evaluated ReAct and static compression baselines. In the *CompactionBench* preprint, Liu et al. (2026) evaluated successive changes to the same repository using executable tests. With GPT-5.6 Sol, summarising completed parts of the interaction in the background while keeping recent activity available yielded 77.95% mean task accuracy, compared with 73.04% for the synchronous baseline using the lower trigger threshold. The first result is for a system trained to choose when to maintain its context. The second is a comparison of policies for preparing and retaining summaries within the tested harness. These results inform different decisions about compaction, and each comparison depends on its task and baseline.

Table 2.3 compares when the information is needed and what each study measures. In particular, a handoff preserves progress on the same issue, while subtask memory supplies experience from earlier issues. That difference matters when interpreting reductions in takeover effort and gains in benchmark resolution.

Across these studies, better access to a specific API can improve call validity, a handoff can reduce repeated investigation, and some memory and compaction policies can improve benchmark task outcomes. These effects may occur at different stages of development, and gains in one measure need not be accompanied by gains in another, as the handoff experiment illustrates. This motivates comparing the delivered code and its validation under the two workflows in this study.
