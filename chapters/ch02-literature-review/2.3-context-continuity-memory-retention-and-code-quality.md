### 2.3 Context Continuity, Memory Retention, and the Quality of Agent-Assisted Code

A coding agent may need the same requirement or repository fact at several points in a task. For example, an agent investigating a login issue might discover that a shared authentication helper is also used by another application. That finding matters when the agent chooses where to make the change and when it decides which behaviour to test. This section examines how coding agents receive and retain such information and what existing studies show about the resulting code. It then relates that evidence to the study's two measures, defect density and final end-to-end (E2E) test pass rate.

#### 2.3.1 Context Continuity and Risks to Agent-Assisted Code

Section 2.1.3 distinguishes the capacity of a context window from the model's ability to use its contents. For a coding agent, an important fact may be missing from the current input because the agent has yet to inspect the relevant file. It may also be present in the input and still be overlooked. Liu et al. (2024) found in question-answering and retrieval tasks that model performance often declined when relevant information appeared in the middle of a long input. Du et al. (2025) observed performance declines as input length increased in controlled experiments that included coding tasks, even when models could retrieve the relevant information. These experiments support a distinction between making information available and using it successfully. They do not measure the frequency of code defects in development sessions.

Compaction introduces a separate question about what survives as a task progresses. Anthropic documents that Claude Code can automatically summarise conversation history as the context window approaches its limit and reload certain sources, including project instructions from the root `CLAUDE.md` file (Anthropic, n.d.-a). A repository file can be read again. If an earlier decision was recorded only in the conversation, it may need to be recovered when the summary omits it. Wang et al. (2026) distinguish the decision to compress, the information retained during compression, and the ability to access that information later. This distinction also matters between sessions. Claude Code supports persistent project instructions and, when enabled, auto memory that can load an index at the start of a session and read detailed notes on demand (Anthropic, n.d.-b). The availability of these mechanisms leaves a practical question about whether the next step receives the particular decisions, constraints, and unresolved issues it needs.

A concrete example is an agent generating a call to a project API that does not exist. Zhang et al. (2025) identified insufficient awareness of project context as one possible contributor to hallucinations in repository-level code generation. Jain et al. (2025) varied the API documentation supplied to a model and found changes in how often it generated valid calls. That experiment establishes an effect of the supplied documentation in its benchmark. Its validity measure also covers syntax and argument errors, so the reported difference cannot be attributed entirely to fabricated APIs. Whether compaction or information loss across sessions increases this particular type of error in Claude Code remains open.

#### 2.3.2 Existing Approaches and Empirical Evidence

One approach is to retrieve code or documentation when it is needed. RepoCoder uses an initial completion to refine subsequent retrieval and improves repository-level completion over both an in-file baseline and a simpler retrieval approach (Zhang et al., 2023). De-Hallucinator uses a related idea to look up project-specific API references suggested by the model's first prediction. Eghbali and Pradel (2024) reported better API prediction for Python completion and corrections to some JavaScript tests that had initially failed with errors associated with hallucinated APIs. These studies evaluate specific generation tasks. For an agent carrying out a development task, the value of retrieval also depends on whether the retrieved material is relevant to the step at which the agent uses it.

Jain et al. (2025) illustrate this trade-off in CloudAPIBench. When StarCoder2-3B received the correct API specification through oracle retrieval, the mean valid invocation rate increased from 41.80% to 86.82%. However, on the high-frequency API subset, the rate decreased from 84.39% without augmentation to 67.32% with one document retrieved at 50% precision. The first comparison supplies the correct specification by design. The second shows how imperfect retrieval can degrade performance in the tested setting. Context reduction can also remove useful material. In RepoExec, Hai et al. (2025) found that retaining the full dependency context gave the best performance among their tested context settings. Le-Anh et al. (2026) extended retrieval to external library dependencies and reported gains in functional correctness on repository code-generation benchmarks. These experiments concern package and library dependencies. In this study, the relevant dependencies can also span internal front-end repositories.

Memory and handoff mechanisms address what to retain for later use. KC and Budathoki (2026) compared coding agents resuming interrupted repository tasks with access to the repository alone, a raw interaction trace, a summary, or structured notes. Providing handoff context reduced rediscovery effort relative to repository-only takeover, while the effect on the proportion of tasks solved varied by successor model. Shen et al. (2026) studied a different use of memory in which agents retrieved experience from earlier tasks at the level of individual subtasks. On SWE-bench Verified, their method improved mean Pass@1 by 4.7 percentage points over the agents without memory across the tested model backbones. The first study concerns resuming the same work. The second concerns reusing experience on a different issue. Their findings provide separate reasons to examine what information is retained and how it is made available.

Other work changes how context is maintained within a session. In *Context as a Tool*, Liu et al. (2025) trained an agent to initiate compression during a task. The resulting system solved 57.6% of SWE-bench Verified issues and outperformed the study's ReAct and static compression baselines. The result applies to the trained system and its evaluation setup. CompactionBench, a preprint by Liu et al. (2026), used successive changes to the same repository and executable tests to compare compaction policies. The authors report a mean task accuracy of 77.95% for their asynchronous progressive method, compared with 73.04% for the synchronous baseline that compacted at the lower threshold. There is also evidence that some ways of adding persistent context yield little benefit. Gloaguen et al. (2026) reported that supplying repository-level instruction files did not generally improve task success in their evaluation. These results support treating retrieval, memory, and compaction as design choices whose effects depend on their implementation and the task.

#### 2.3.3 Research Gap and Evaluation Rationale

The studies reviewed here report outcomes such as valid API calls, repository-level completion, issue resolution, or the effort required to resume a task. They provide evidence about particular mechanisms under their evaluation conditions. They leave open how the conventional prompt-based workflow and the structured agent orchestration workflow compare on defect density and final E2E test pass rate when both use Claude Code for enterprise front-end development spanning multiple repositories.

The two measures capture different observations. Final E2E pass rate is the proportion of the task's specified cases reported as passing before development handoff, after any permitted test-script corrections. Both workflows use the same test-case format, execution tool, and intended correction limit. Each task has its own cases, from which the agent generates the scripts. In the *TestSuiteBench* preprint, Egashira et al. (2026) found that agent-generated suites could run successfully against reference implementations and still miss faults introduced to test specified behaviour. That finding concerns a different test-generation setting, but it illustrates why passing tests provide evidence limited to the behaviours the scripts actually check. Defect density provides a second observation by relating confirmed defects linked to the task to the amount of changed production code. Its interpretation depends on which defects are recorded and on the size of the change, particularly when a small change gives a small denominator.

RQ2 therefore asks how these two measures differ between the workflows. The comparison evaluates each workflow as used in development. Trade-Harness changes how several activities are organised, including context handling and validation, so the design cannot attribute a difference to any one practice. The comparison measures development outcomes. Estimating hallucination frequency would require identifying and classifying hallucinations separately.
