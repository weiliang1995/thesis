#### 2.1.4 Harness Engineering

In the email example from the previous sections, the user has specified the intended audience and tone and has supplied the information needed for a project update. The task can extend beyond drafting the message. If the user also asks the agent to suggest a meeting time based on their calendar, the agent needs access to current availability and a way to retrieve it. If there is no suitable time, it may need to check another period or ask the user for a preference before completing the draft. Providing clear instructions and relevant background remains useful, but the task now also involves tool access, decisions made during execution, and checks on the result. This example illustrates why the engineering of an agent extends beyond the content of its prompt.

The system surrounding a model is often called an agent harness. Trivedy (2026a) uses the term broadly to include the code, configuration, tools, state, and execution logic that enable a model to act in an environment. Under this broad definition, a coding agent such as Claude Code already has a harness: it can inspect files, run commands, and use their results to decide what to do next. Developers can also build project-specific arrangements around those native capabilities. In this study, harness engineering refers to the deliberate organisation of information, tools, task state, execution steps, and feedback for software development tasks. This usage overlaps with prompt and context engineering rather than replacing them. A project instruction may guide the agent's behaviour, while the surrounding workflow determines how that instruction is used alongside tools and checks.

Accounts of harness engineering differ in emphasis. Hashimoto (2026) describes a practice of responding to repeated agent mistakes by improving project instructions or writing tools that help the agent verify its work. For example, an instruction file may tell the agent which command to run, while a test script can report whether the resulting change meets a specific requirement. In this account, guidance and executable feedback are both parts of the harness. An instruction can influence what the agent attempts, but it does not itself establish that the intended outcome has been achieved.

Continuity is more prominent in Young's (2025) account of Anthropic's experiment with long-running application development. The Claude Agent SDK already supplied a general-purpose agent harness and context compaction. In the reported experiment, however, compaction alone did not always give a later session a clear account of unfinished work. The team used an initial setup session, followed by coding sessions that made incremental progress and left records for subsequent sessions. These records helped the agent distinguish completed work from work still to be done. This is an example of designing the environment and handoff around an existing agent, rather than assuming that an agent's current conversation will be sufficient throughout a long task.

LangChain and OpenAI illustrate further aspects of the same practice. LangChain describes harness design in terms of system instructions, tools, and middleware that can intervene during execution. In one coding-agent experiment, it added support for checking work before completion and for recognising repeated edits that were not making progress. With the model held fixed, LangChain reported an increase from 52.8 to 66.5 on Terminal Bench 2.0 after changes to its harness (Trivedy, 2026b). This is evidence about that agent in a benchmark setting, not a measure of enterprise delivery or software quality. OpenAI's account focuses on making repository knowledge accessible to an agent and encoding selected architectural rules in linters and CI checks (Lopopolo, 2026). These examples show different ways to organise the information an agent uses and the feedback it receives; they do not prescribe a single architecture for every development setting.

Trade-Harness organises these concerns into six functional layers: Information Boundary, Tool System, Execution Orchestration, Memory and State, Evaluation and Observability, and Constraints, Validation and Recovery. This six-layer structure is the framework used in this study, not a taxonomy proposed jointly by the cited authors. The layers distinguish responsibilities within a development workflow, although a single artifact may serve more than one purpose. For example, a test runner is a tool, its output is evidence about the change, and a failed test may lead to a correction step. The following discussion explains each layer and relates it to the engineering practices described above.

The first layer, Information Boundary, concerns which information is relevant and available to the agent for a task. In front-end development, a requested change may depend on requirements, source files, shared interfaces, and conventions distributed across repositories. The agent needs a way to locate the materials relevant to the change without treating all available files as equally useful. Lopopolo (2026) describes giving Codex a navigable map of repository knowledge and exposing further detail as needed rather than placing all instructions in one large file. In Trade-Harness, the information boundary establishes the scope and sources of task information. It does not imply that selecting appropriate information guarantees that the agent will interpret or follow it correctly.

The second layer, Tool System, concerns how the agent interacts with those sources and with the development environment. A calendar query in the email example makes current availability accessible. In a coding task, corresponding operations include finding files, reading code, running commands, and invoking tests. Hashimoto (2026) describes adding scripts that allow an agent to check its output, while Trivedy (2026a) includes tools and execution facilities within the harness. Trade-Harness treats the tools available to the agent and the results returned by those tools as a distinct concern. Tool access enables an action, but it does not specify when the action should occur or what the workflow should do with an unsuccessful result.

The third layer, Execution Orchestration, concerns how a development task moves between investigation, implementation, and verification. Anthropic (2024) distinguishes workflows, in which code defines the path through model and tool calls, from agents, which can choose actions dynamically. The two arrangements can be combined: a workflow may establish stages and checkpoints while the agent determines how to carry out the work within a stage. LangChain's build-and-verify sequence provides one example of making a check part of the execution process rather than leaving it to an informal final review (Trivedy, 2026b). Trade-Harness uses this layer to organise the progression of a task without assuming that every decision can be specified in advance.

The fourth layer, Memory and State, concerns information that must remain available as the task progresses. The agent may need to retain what it has changed, which checks have run, which issues remain unresolved, and which decisions require developer input. Young (2025) describes progress artifacts and version history that allow later coding sessions to resume work; Lopopolo (2026) similarly describes versioned plans and decision records in the repository. In Trade-Harness, this layer preserves task progress and handoff information. Its role differs from Information Boundary: the latter concerns what the agent needs to access for the task, while Memory and State concerns what the ongoing task has produced and what must be carried forward.

The fifth layer, Evaluation and Observability, concerns the evidence available to assess the agent's actions. Test results, command output, logs, and execution records can show what was attempted and whether a check passed. LangChain used agent traces to investigate failure patterns, including omitted verification and repeated unsuccessful edits (Trivedy, 2026b). OpenAI describes making application behaviour, logs, and metrics accessible so that its agents can examine the effects of changes (Lopopolo, 2026). Trade-Harness places the capture and examination of such evidence in this layer. A passing check supports the properties covered by that check; it does not by itself establish that every requirement has been met.

The sixth layer, Constraints, Validation and Recovery, concerns how requirements are checked and how the workflow responds to an unsatisfactory result. Some constraints can be checked by tests or structural rules, while others require a developer's judgement. OpenAI reports using custom linters and structural tests to enforce selected architectural boundaries (Lopopolo, 2026). Hashimoto (2026) also emphasises tools that let an agent identify mistakes and revise its work. In Trade-Harness, this layer specifies applicable checks, the bounds of further correction, and circumstances in which an unresolved issue returns to the developer. Evaluation and Observability make a problem visible; Constraints, Validation and Recovery determine what may happen next. An automated signal is useful only when it is interpreted in relation to the task and the workflow has an appropriate response.

The six layers describe how Trade-Harness structures the use of capabilities that a coding agent may already possess. They do not imply that the prompt-based workflow lacks repository access, tool use, context management, or testing. As discussed in Section 2.1.1, both workflows in this study use an agent-capable coding tool; the comparison concerns how its activities are organised. The six-layer structure gives a rationale for that organisation, but its effects remain open to evaluation. Additional stages, records, and checks may help maintain continuity or identify errors, while also requiring developer effort, tool calls, and tokens. Anthropic (2024) notes that more elaborate agentic systems can trade latency and cost for task performance. The following sections therefore examine delivery efficiency, software quality, and computational cost separately before synthesising the evidence relevant to Trade-Harness.
