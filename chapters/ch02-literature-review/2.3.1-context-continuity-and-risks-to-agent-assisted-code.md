### 2.3 Context Continuity, Memory Retention, and the Quality of Agent-Assisted Code

A coding agent may need the same requirement or repository fact at several points in a task. For example, an agent investigating a login issue might discover that a shared authentication helper is also used by another application. That finding matters when the agent chooses where to make the change and when it decides which behaviour to test. This section examines how coding agents receive and retain such information and what existing studies show about the resulting code. It then relates that evidence to the study's two measures, defect density and final end-to-end (E2E) test pass rate.

#### 2.3.1 Context Continuity and Risks to Agent-Assisted Code

A coding agent can miss a dependency because it has yet to inspect the file where it is defined. The agent can also overlook a dependency even when that file is already in its context. As discussed in Section 2.1.3, Liu et al. (2024) found that moving relevant information to the middle of a long input often reduced performance on question answering and retrieval tasks. Du et al. (2025) reported declines across tasks including coding as input length increased, even in settings where the models could retrieve the relevant information. Raju et al. (2026), in a preprint on bug fixing, supplied the files changed in the reference patches for 100 SWE-bench Verified tasks. In the 64,000-token setting, some patches generated in a single attempt targeted files that did not exist. The patch examples show that supplying the relevant files can still leave room for errors. The setup evaluates single-attempt generation, so it leaves open how an agent would recover through further inspection and testing.

Compaction changes what a model receives as it continues a session. Anthropic documents that Claude Code can summarise conversation history as the context window approaches its limit and reload sources such as project instructions in the root `CLAUDE.md` file (Anthropic, n.d.-a). In the login example, a constraint agreed during the conversation, such as preserving the existing error response, could be omitted from the summary even if the overall task is retained. Y. Wang et al. (2026) distinguish information lost during compression from information that survives but is difficult to access afterwards. In a separate preprint, Z. Wang et al. (2026) measured whether compacted contexts retained user constraints and used follow-up probes to assess whether models followed them. On a subset with 126 naturally occurring constraints from GitHub issues and their associated coding agent traces, none of the compactors tested retained more than 28.6% of those constraints. That result measures preservation under the study's compaction setups. It does not estimate how often Claude Code loses constraints or how often an omission produces a code defect.

Resuming the same task in another session requires recovering the state of the work. A diff may show that the login handler was edited, while the reason for that change or the fact that the second application has yet to be tested may only appear in earlier discussion. Anthropic documents persistent project instructions and optional auto memory that can load an index at the start of a session and read detailed notes as needed (Anthropic, n.d.-b). Project instructions can carry conventions across tasks, while a handoff can describe progress and pending checks for a particular issue. KC and Budathoki (2026) isolate the handoff problem by giving successor agents the same partial repository state and varying what they can see about the previous attempt. Their design illustrates why the repository state and the record of how the task reached that state are useful to examine separately.

Information that carries across sessions may also become outdated. Mehtiyev et al. (2026) examined three examples in active open-source repositories, involving a test command, a code location, and a procedure for adding a component. In their preprint, the agents attempted maintenance tasks under stale, corrected, and removed versions of the relevant instruction, using the same code and task for each comparison. With the outdated test command, Claude Sonnet 5.5 needed about two additional tool calls per run compared with the corrected command. The authors did not detect a corresponding difference in the other two cases. The result concerns recovery effort from outdated repository instructions, and it illustrates why continuity also depends on whether the information provided is still current.

One observable error in generated code is a call to a project API that does not exist. Zhang et al. (2025) identified insufficient awareness of project context as one possible contributor to hallucinations in repository-level code generation. Jain et al. (2025) varied the API documentation supplied to a model and found changes in the rate of valid calls. Their measure includes syntax and argument errors as well as calls to nonexistent APIs. The experiment supports a link between the supplied API information and call validity in that benchmark. How often compaction, a handoff, or an outdated note contributes to fabricated APIs in Claude Code remains open.
