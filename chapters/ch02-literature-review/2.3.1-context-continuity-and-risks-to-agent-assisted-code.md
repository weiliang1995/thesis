### 2.3 Context Continuity, Memory Retention, and the Quality of Agent-Assisted Code

A coding agent may need the same requirement or repository fact at several points in a task. For example, an agent investigating a login issue might discover that a shared authentication helper is also used by another application. That finding matters when the agent chooses where to make the change and when it decides which behaviour to test. This section examines how coding agents receive and retain such information and what existing studies show about the resulting code. It then relates that evidence to the study's two measures, defect density and final end-to-end (E2E) test pass rate.

#### 2.3.1 Context Continuity and Risks to Agent-Assisted Code

Section 2.1.3 distinguishes the capacity of a context window from the model's ability to use its contents. For a coding agent, an important fact may be missing from the current input because the agent has yet to inspect the relevant file. It may also be present in the input and still be overlooked. Liu et al. (2024) found in question-answering and retrieval tasks that model performance often declined when relevant information appeared in the middle of a long input. Du et al. (2025) observed performance declines as input length increased in controlled experiments that included coding tasks, even when models could retrieve the relevant information. These experiments support a distinction between making information available and using it successfully. They do not measure the frequency of code defects in development sessions.

Compaction introduces a separate question about what survives as a task progresses. Anthropic documents that Claude Code can automatically summarise conversation history as the context window approaches its limit and reload certain sources, including project instructions from the root `CLAUDE.md` file (Anthropic, n.d.-a). A repository file can be read again. If an earlier decision was recorded only in the conversation, it may need to be recovered when the summary omits it. Wang et al. (2026) distinguish the decision to compress, the information retained during compression, and the ability to access that information later. This distinction also matters between sessions. Claude Code supports persistent project instructions and, when enabled, auto memory that can load an index at the start of a session and read detailed notes on demand (Anthropic, n.d.-b). The availability of these mechanisms leaves a practical question about whether the next step receives the particular decisions, constraints, and unresolved issues it needs.

A concrete example is an agent generating a call to a project API that does not exist. Zhang et al. (2025) identified insufficient awareness of project context as one possible contributor to hallucinations in repository-level code generation. Jain et al. (2025) varied the API documentation supplied to a model and found changes in how often it generated valid calls. That experiment establishes an effect of the supplied documentation in its benchmark. Its validity measure also covers syntax and argument errors, so the reported difference cannot be attributed entirely to fabricated APIs. Whether compaction or information loss across sessions increases this particular type of error in Claude Code remains open.
