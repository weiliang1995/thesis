#### 2.3.3 Research Gap and Evaluation Rationale

The studies reviewed here report outcomes such as valid API calls, repository-level completion, issue resolution, or the effort required to resume a task. They provide evidence about particular mechanisms under their evaluation conditions. They leave open how the conventional prompt-based workflow and the structured agent orchestration workflow compare on defect density and final E2E test pass rate when both use Claude Code for enterprise front-end development spanning multiple repositories.

The concern raised in Section 1.2.2 extends to both implementation and validation. A missed requirement may be absent from the delivered change or from the checks used to evaluate it. Duan et al. (2026) reported regression test pass rates alongside a defect rate derived from Jira reports linked to feature commits in their study of AI-assisted development. This provides a precedent for examining both outcomes. For RQ2, the final E2E test pass rate records the share of specified cases reported as passing before development handoff. Defect density relates the confirmed defects linked to a task to the amount of production code changed.

The final test result depends in part on how the agent translates the specified cases into executable scripts. In the *TestSuiteBench* preprint, Egashira et al. (2026) found that many agent-generated tests passed on reference implementations, yet the generated suites missed faults introduced to test specified behaviour. The study used a different test generation setting, but it illustrates why a passing test gives evidence about the behaviour its script actually checks. Confirmed defects provide a separate observation whose interpretation depends on which defects are recorded and on the size of the change.

RQ2 therefore asks how these two measures differ between the workflows. The comparison evaluates each workflow as used in development. Trade-Harness changes how several activities are organised, including context handling and validation, so the design cannot attribute a difference to any one practice. The comparison measures development outcomes. Estimating hallucination frequency would require identifying and classifying hallucinations separately.
