#### 2.3.3 Research Gap and Evaluation Rationale

The studies reviewed here report outcomes such as valid API calls, repository-level completion, issue resolution, or the effort required to resume a task. They provide evidence about particular mechanisms under their evaluation conditions. They leave open how the conventional prompt-based workflow and the structured agent orchestration workflow compare on defect density and final E2E test pass rate when both use Claude Code for enterprise front-end development spanning multiple repositories.

The two measures capture different observations. Final E2E pass rate is the proportion of the task's specified cases reported as passing before development handoff, after any permitted test-script corrections. Both workflows use the same test-case format, execution tool, and intended correction limit. Each task has its own cases, from which the agent generates the scripts. In the *TestSuiteBench* preprint, Egashira et al. (2026) found that agent-generated suites could run successfully against reference implementations and still miss faults introduced to test specified behaviour. That finding concerns a different test-generation setting, but it illustrates why passing tests provide evidence limited to the behaviours the scripts actually check. Defect density provides a second observation by relating confirmed defects linked to the task to the amount of changed production code. Its interpretation depends on which defects are recorded and on the size of the change, particularly when a small change gives a small denominator.

RQ2 therefore asks how these two measures differ between the workflows. The comparison evaluates each workflow as used in development. Trade-Harness changes how several activities are organised, including context handling and validation, so the design cannot attribute a difference to any one practice. The comparison measures development outcomes. Estimating hallucination frequency would require identifying and classifying hallucinations separately.
