#### 2.1.2 Prompt Engineering

An instruction such as “Make this email more professional” may appear straightforward, yet the meaning of professionalism can vary depending on the intended audience, communication purpose, and social context. For instance, an email addressed to a supervisor may require a different tone from one addressed to a colleague or a customer. Human communication often relies on shared knowledge, prior experience, and implicit expectations that are not necessarily expressed in the instruction itself. When a similar instruction is given to a large language model (LLM), the model may interpret the request and generate a reasonable response. However, its interpretation may not necessarily align with the user's intended outcome. This illustrates a fundamental challenge in natural language interaction with LLMs: how to communicate task requirements and user intentions effectively through input instructions.

Prompt engineering addresses this challenge through the deliberate design and refinement of inputs to guide model behaviour and output without modifying the underlying model parameters (Liu et al., 2026; Schulhoff et al., 2025). Rather than relying on a general instruction, users can specify the task objective, relevant requirements, constraints, and expected outcomes. For example, the previous instruction could be refined to “Rewrite this email using a polite and professional tone suitable for communicating with a supervisor. Keep it concise, preserve the original meaning, and avoid overly formal language.” Compared with the original instruction, the refined prompt communicates the intended audience, tone, and output constraints more explicitly. Although such refinement does not guarantee that the generated response will fully satisfy the user's expectations, it reduces ambiguity in the task specification and provides clearer guidance for the model.

Beyond the refinement of instructions, prompt engineering encompasses a range of techniques designed to influence model behaviour. Schulhoff et al. (2025) identified 58 text-based prompting techniques in their systematic survey, covering approaches such as in-context learning, thought generation, decomposition, ensembling, and self-criticism. Representative techniques include zero-shot prompting, which specifies a task without providing demonstrations; few-shot prompting, which incorporates examples to guide the model; and chain-of-thought prompting, which encourages intermediate reasoning. However, the effectiveness of these techniques may vary across tasks and model configurations. In their evaluation using GPT-3.5-turbo on a subset of the Massive Multitask Language Understanding (MMLU) benchmark, Schulhoff et al. (2025) reported that zero-shot chain-of-thought prompting achieved lower accuracy than standard zero-shot prompting, whereas few-shot chain-of-thought prompting achieved the highest accuracy among the evaluated configurations. This finding illustrates that increasing the complexity of a prompting technique does not necessarily improve task performance. Complementing this technical classification, Liu et al. (2026) proposed four dimensions of prompt engineering: profile and instruction, knowledge, reasoning and planning, and reliability. Their framework highlights that prompt engineering extends beyond instruction formulation to encompass the incorporation of external knowledge, guidance of reasoning processes, and considerations of output reliability.

In the context of software engineering, these principles can be applied to guide LLM-based agents in performing development tasks. Consider a developer instructing an agent to “Fix the login issue.” Such an instruction does not specify the observed behaviour, expected outcome, or constraints governing the implementation. A more structured prompt could be formulated as follows: “Investigate why users are redirected back to the login page after successful authentication. Identify the root cause before modifying the code, follow the existing authentication architecture, avoid unrelated changes, and add appropriate regression tests.” This example demonstrates how prompt engineering can be used to communicate specific task requirements, guide the investigation process, establish implementation constraints, and define expected deliverables. These considerations reflect several of the prompt design dimensions identified by Liu et al. (2026).

Nevertheless, providing explicit instructions does not necessarily ensure that an agent possesses the information required to execute a task. In the login example, instructing the agent to follow the existing authentication architecture does not, by itself, provide knowledge of that architecture. The agent may need access to relevant source code, architectural documentation, API specifications, error logs, and existing test cases to investigate the issue effectively. While such information can be incorporated into prompts, software engineering tasks may involve information distributed across multiple sources, as well as new information generated throughout task execution. Consequently, the engineering challenge extends beyond formulating appropriate instructions to determining what information should be made available to the agent, how that information should be organized, and when it should be updated. These considerations motivate the discussion of context engineering in the following section.
