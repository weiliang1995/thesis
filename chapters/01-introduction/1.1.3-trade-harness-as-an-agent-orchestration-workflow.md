#### 1.1.3 Agent Orchestration Workflow in Software Engineering

Trade-Harness is designed as a structured agent orchestration workflow for front-end development. Instead of changing the underlying language model, it introduces a controlled process for managing task scope, project context, tool access, execution stages, and validation.

The main idea is to use predefined workflow rules to guide agent execution. Each stage defines the information and tools made available to the agent, as well as the conditions that must be satisfied before proceeding. The agent can still make decisions and generate code within those boundaries, but progression between stages is governed by the workflow rather than relying only on the agent's own judgement.

This approach does not make the LLM deterministic. Its purpose is to provide a more predictable execution structure around non-deterministic agent behaviour.

Trade-Harness consists of six functional layers, as shown in Table 1.1.

*Table 1.1 Six Layers of Trade-Harness*

| **Layer** | **Purpose in Trade-Harness** |
|---|---|
| L1 Information Boundary | Defines the task scope and limits the agent to relevant requirements, repositories, files, and architectural information. |
| L2 Tool System Extraction | Provides controlled access to project artefacts, development tools, source files, and dependencies. |
| L3 Execution Orchestration Loops | Organizes task planning, task decomposition, staged execution, and feedback loops. |
| L4 Memory and State Management | Keeps task state, handover notes, intermediate decisions, and useful context across workflow stages. |
| L5 Evaluation and Observability | Records validation results, execution traces, and agent decisions so developers can inspect the workflow. |
| L6 Constraints and Validation | Applies validation rules, detects errors, and supports correction before generated output is accepted. |

For example, a front-end task may require changes to a shared component and the application that consumes it. Trade-Harness is designed to identify relevant repositories and dependencies, provide task-specific context and tools, and organize implementation and validation. If a predefined check fails, the result can be used to guide a further correction attempt before the workflow proceeds.

The six layers work together to support this process; they are not six sequential development stages. Trade-Harness also does not require multiple agents for every task. Agent assignment and execution can vary according to the task's requirements.

While the workflow is intended to support coordination and validation, additional planning, context handling, and execution checks may consume extra time and tokens. Whether the benefits outweigh this overhead is examined through the comparative evaluation in this study.
