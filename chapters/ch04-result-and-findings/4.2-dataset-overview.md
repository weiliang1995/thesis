## 4.2 Dataset Overview

> **Draft status — provisional dataset.** This analysis includes all 290 tasks and ten developers in the current Google Sheet. The Methodology branch still describes a two-developer design; the final participant and task inclusion rules require confirmation before submission. The figures below are descriptive observations, not causal estimates.

The Jira issue was used as the unit of observation in this preliminary dataset. The current worksheet contains **290 issues**, with status timestamps spanning **2026-08-03 to 2026-10-23**. Each issue is labelled with one workflow condition. The dataset was checked for duplicate issue keys, available status transitions and consistency with the rounded lead-time values recorded in the task table. No duplicate task keys or unmatched start/completion transitions were found.

### 4.2.1 Task Characteristics and Allocation

The baseline condition contains **159 issues** (54.8%), while Trade-Harness contains **131 issues** (45.2%). Tasks were grouped by the pre-task estimated development effort defined in the Methodology: simple (at most one working day), medium (more than one and up to four working days), and complex (more than four working days). All recorded effort estimates were consistent with their assigned complexity category.

**Table 4.1. Task distribution by workflow and estimated complexity**

| Complexity | Baseline (n) | Trade-Harness (n) | Total (n) |
|---|---:|---:|---:|
| Simple | 124 | 104 | 228 |
| Medium | 31 | 22 | 53 |
| Complex | 4 | 5 | 9 |
| **Total** | **159** | **131** | **290** |

Simple tasks account for **228 of 290 issues** (78.6%), compared with 53 medium (18.3%) and 9 complex (3.1%) issues. Both workflow groups are dominated by simple tasks; the complex-task subgroup contains only four baseline issues and five Trade-Harness issues. Consequently, the overall results primarily describe simpler development work, and estimates for complex tasks are sensitive to individual issues.

The worksheet labels 185 tasks as *feature* and 105 as *enhancement*. The tasks cover Futures (72), Options (55), Spot (57), TradFi (67), and Tools (39). Differences in business domain, task scope and dependencies may influence the comparisons even within the same complexity category. No random allocation is assumed.

### 4.2.3 Record Matching, Exclusions and Completeness

The current workbook contains task-level records and separate status-history, defect, developer and developer-summary worksheets. The status history provides **626 transitions** for the 290 issues. **23 issues were reopened** (15 baseline; 8 Trade-Harness), producing additional development-state transitions. For those issues, the stored lead-time interval runs from the first recorded *In Progress* to the final recorded *Development Complete* transition. This includes elapsed time between repeated development cycles and requires confirmation as the final treatment of reopened work.

**Table 4.3. Usable issues for each outcome in the provisional dataset**

| Outcome | Baseline usable (n) | Trade-Harness usable (n) | Missing or undefined values |
|---|---:|---:|---|
| Development lead time | 159 | 131 | No missing status timestamps in the current task records |
| Final task-level E2E pass rate | 158 | 130 | One missing final E2E result in each workflow |
| Defect density (per 1,000 changed production LOC) | 158 | 131 | One baseline issue has zero production changed LOC; the ratio is undefined |
| Changed production LOC per million tokens | 159 | 130 | One Trade-Harness issue lacks linked token usage |
| Gateway-recorded LLM cost per completed issue | 159 | 130 | One Trade-Harness issue lacks linked gateway cost |
| E2E test-script correction loops (supplementary) | 158 | 130 | One missing loop record in each workflow |

Missing E2E reports are not assigned a pass rate of zero; missing gateway data is not interpreted as zero token consumption or cost. The zero-production-LOC task remains in the issue dataset but has no defined defect-density ratio. The valid sample size therefore differs across metrics, and later sections must display the relevant denominator.
