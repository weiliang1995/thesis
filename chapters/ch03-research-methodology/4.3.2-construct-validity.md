#### 4.3.2 Construct Validity

The quality measures cover only part of what software quality means in practice. Final E2E pass rate shows whether an implementation satisfies the task-specific cases available at development handoff; defect density captures confirmed defects linked to the delivered change. Neither measure directly evaluates maintainability, security, or all possible integration failures. Although both workflow conditions use the same JSON test-case format and Playwright MCP procedure, each feature has different test requirements and coverage. A higher pass rate therefore does not necessarily mean that more difficult behaviour was tested. The final report also follows the permitted correction loops, so it does not represent the initial quality of the agent's generated test code.

Defect density is normalized by changed lines of production code rather than by the size of an entire module. This makes the measure suitable for task-level comparison, but the ratio can become large for a small change with only one or two defects. Such valid observations are retained and interpreted together with raw defect counts and changed LOC. The number of defects found also depends on their being reported and linked to the feature in Jira, and tasks completed earlier may have a longer period in which defects can be discovered before data extraction. The defined cutoff and traceable issue links make the data scope explicit but cannot guarantee that every latent defect is observed.

Delivery lead time measures elapsed time from *In Progress* to *Development Complete*. It includes developer-owned work and any interruptions within that interval, not only active coding or agent execution. Changed LOC per million tokens measures the amount of final code change relative to recorded model usage; a larger value is not necessarily better code or greater functional value. Token cost per issue measures recorded LLM charges, not labour or infrastructure costs. These operational definitions are used consistently, but each remains a proxy for a broader engineering outcome.

Finally, Trade-Harness changes several aspects of workflow coordination together, including task decomposition, context and state handling, tool execution, and validation. The study does not disable and re-enable these layers separately. Differences in defect density, test results, or other outcomes therefore cannot establish that context or memory management alone caused the observed result. The findings concern the complete orchestrated workflow rather than the effectiveness of any single layer.
