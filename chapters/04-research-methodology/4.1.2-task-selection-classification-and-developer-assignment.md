#### 4.1.2 Task Selection, Classification and Developer Assignment

The study uses tasks from the team's normal development work rather than tasks created specifically for the experiment. These include feature requirements raised by product managers, bug fixes, and refactoring work arising from technical debt. Tasks are recorded in Jira. To be included, a task must involve front-end development and have a traceable Jira record linked to code changes in GitLab. Backend-only tasks, mobile application development, architectural redesign, product research, and tasks without sufficient traceable records are excluded. The treatment of incomplete records for individual outcome measures is described in Section 4.2.

Before implementation begins, eligible tasks are classified as simple, medium, or complex. The primary criterion is the technical lead's estimate of the development effort required, informed by the anticipated scope of changes and technical dependencies. Wood (1986) distinguishes component and coordinative dimensions of task complexity, while Jørgensen (2004) reviews expert judgement as a method of estimating software development effort. These studies inform the use of task scope, dependencies, and expert-based effort estimation in the classification. They do not prescribe the time thresholds adopted here. The thresholds in Table 4.1 are operational definitions for this study, not a standardized measure of task complexity.

*Table 4.1 Task Complexity Classification*

| **Complexity Level** | **Estimated Effort** | **Supporting Task Characteristics** | **Examples** |
|---|---|---|---|
| Simple | ≤ 1 working day | Localized front-end changes with limited scope and few dependencies | CSS or layout adjustments, announcement modal, advertisement banner, minor UI updates |
| Medium | > 1 to ≤ 4 working days | Changes involving several related components, application state, or API integration | Order query panel with backend support, dashboard data visualization |
| Complex | > 4 working days | Larger feature or module changes involving substantial business logic, cross-component coordination, or cross-repository integration | New order type module, end-to-end feature with new APIs and front-end module changes |

Estimated effort determines the classification band; the supporting characteristics guide the estimate but are not mandatory conditions for every task in a category. A task does not have to involve a backend API to be classified as medium, for example. The classification is made from the task requirements before development and is not recalculated using the observed delivery lead time.

Two developers from the front-end development team participate in the study. Developer A has approximately two years of front-end experience, and Developer B has approximately three years. Both are familiar with the selected trading system and have experience using Claude Code.

The technical lead assigns tasks to developers based on the relevant business domain, estimated work, and team availability. During the 12-week study, the technical lead also allocates the workflow condition. For each developer and each task-complexity level, the allocation aims to distribute tasks as evenly as practical between the conventional developer-managed prompt-based workflow and Trade-Harness. Each developer therefore works with both conditions on different tasks. This allocation is not randomized, and operational requirements may prevent identical task counts or task characteristics across conditions. The resulting distribution will be considered when comparing outcomes.
