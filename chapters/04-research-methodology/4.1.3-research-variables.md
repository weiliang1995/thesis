#### 4.1.3 Research Variables

This study compares two ways of coordinating AI-assisted front-end development tasks. The independent variable is the development workflow, while the dependent variables describe delivery efficiency, software quality, and computational resource efficiency and cost. Both workflow conditions use the same underlying coding agent and follow the project's development and acceptance requirements.

**Independent Variable**

The independent variable has two conditions: a conventional developer-managed prompt-based workflow (baseline) and Trade-Harness (intervention). Both use Claude Code CLI with Claude Sonnet 4.6 and retain the CLI's native capabilities for planning, repository inspection, code editing, and tool execution. Trade-Harness adds a structured orchestration layer around those capabilities; it does not modify the underlying model. Table 4.2 compares how development activities are managed rather than whether an activity is technically available in each condition.

*Table 4.2 Workflow Condition Comparison*

| **Workflow Management Dimension** | **Baseline: Developer-Managed Workflow** | **Intervention: Trade-Harness** |
|---|---|---|
| Workflow Control | The developer coordinates activities through prompts and Claude Code's native agent capabilities. | Predefined workflow rules coordinate activities and progression between stages. |
| Task Planning and Decomposition | The developer guides planning and task breakdown with assistance from the agent. | Requirements guide structured task decomposition and execution planning under workflow rules. |
| Context and Dependencies | Claude Code inspects repository context, with additional context selected or supplied by the developer. | Repository-aware context assembly identifies and provides relevant information and dependencies for each stage. |
| State and Continuity | Native session context and project instructions are available; the developer coordinates context transfer when needed. | Explicit task state and contextual handovers are managed across workflow stages. |
| Tool and Agent Execution | Claude Code and the developer initiate native tools and MCP calls as needed. | Tool use and agent execution are organized according to the requirements and rules of each stage. |
| Testing and Validation | The developer supplies task-specific JSON test cases and prompts or project instructions for E2E execution and up to three test-script correction loops. | Defined validation stages coordinate E2E execution and enforce up to three test-script correction loops. |
| Observability and Review | The developer reviews tool outputs, test results, and code changes using the available environment. | Structured execution records and validation outcomes support inspection and developer review. |

The two conditions follow the same applicable development requirements and E2E testing procedure. Each task has its own JSON test-case document. In both conditions, the agent uses those task-specific cases to generate E2E test code and execute the tests through Playwright MCP; the same task is not implemented twice. After a failed run, the agent may review and correct problems in the generated test script, but this testing correction loop does not modify business code or change test-case requirements to force a pass. The common procedure specifies a maximum of three such loops. For the baseline, the rule is communicated through developer prompts or project instructions, whereas Trade-Harness applies it through predefined workflow controls. The distinction is how the process is coordinated and enforced, not which testing capabilities are available. Trade-Harness does not require multiple agents for every task, and developer review remains part of both workflows.

**Dependent Variables**

Three groups of dependent variables correspond to the research questions:

- **Delivery efficiency (RQ1):** Development lead time, measured in elapsed days from the Jira transition to *In Progress* until the intermediate *Development Complete* status.
- **Software quality (RQ2):** Final end-to-end (E2E) testing pass rate and defect density, with defect density expressed as confirmed defects per thousand changed lines of production code.
- **Computational resource efficiency and cost (RQ3):** Changed lines of production code per million tokens consumed and LLM token cost per resolved issue.

The definitions, calculations, and data sources for these measures are presented in Section 4.2.

**Controlled Conditions and Other Influencing Factors**

The study uses the same Claude Sonnet 4.6 model, Claude Code CLI, VS Code environment, and applicable team development and testing requirements in both workflow conditions, including the JSON test-case format and the instructed maximum of three test-script correction loops. The comparison does not involve switching between language models or coding tools. Differences in how context is assembled, tools are invoked, and validation is coordinated are part of the workflow conditions and are not held constant.

Task complexity and developer are addressed through the intended balancing procedure described in Section 4.1.2, rather than being treated as fixed conditions. Business domain, task dependencies, and developer familiarity may still affect the observed outcomes. These factors are considered when interpreting the comparison and are discussed further under threats to validity in Section 4.3.
