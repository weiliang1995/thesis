#### 4.1.1 Quasi-Experimental Design

This study uses a 12-week quasi-experimental design to compare two AI-assisted development workflows under normal project conditions. The baseline is a developer-managed prompt-based workflow using Claude Code CLI, while Trade-Harness adds predefined rules for task execution, context handling, and validation. Both workflows use Claude Sonnet 4.6 in the same development environment. The unit of observation is an individual development task, with outcomes measured in delivery efficiency, software quality, and computational cost.

The study takes place in a cryptocurrency trading platform's front-end system, which contains approximately 722,000 lines of code and nearly 70 component libraries maintained by 13 front-end developers. The system includes dependencies across repositories and modules, making it a relevant setting for examining workflow coordination in everyday front-end development.

A fully randomized experiment is not practical in this setting. Development tasks arise from business requirements or maintenance needs, and the technical lead allocates work according to the team's available capacity. The same task cannot reasonably be implemented twice in the production workflow merely to compare the two conditions. Repeating it could also give the second attempt an advantage from knowledge gained during the first. For these reasons, tasks are not randomly assigned or repeated under both workflows. Two developers participate in the comparison, with each using both workflows on different tasks. Tasks are classified by estimated effort and dependency requirements to help interpret differences in their complexity, rather than assuming that tasks assigned to the two conditions are equivalent.

The study procedure is to identify eligible Jira tasks, classify them, assign the developer and workflow condition, complete the development and validation activities, and then extract the corresponding Jira, GitLab, testing, and LLM usage records for comparison. Task selection and assignment are detailed in Section 4.1.2, while the outcome measures and data sources are described in Section 4.2. Because task characteristics, developer familiarity, scheduling, and external dependencies cannot be fully controlled, differences between the workflows will be interpreted as observed associations in this project rather than evidence that orchestration alone caused the outcomes.
