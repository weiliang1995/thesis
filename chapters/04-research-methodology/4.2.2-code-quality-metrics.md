#### 4.2.2 Software Quality Metrics

Software quality is evaluated using the final end-to-end (E2E) test pass rate and defect density for each feature-development task. An E2E test report describes the outcome of agent-assisted validation before development handoff, while defect density captures confirmed defects linked to the delivered change. The study also records E2E test-script correction loop count as a supplementary process measure, rather than as a direct indicator of software quality.

**Final E2E Test Pass Rate**

For each task, the agent generates E2E test code from that task's JSON test-case document and executes the tests through Playwright MCP. The pass rate is taken from the final report after testing is completed or the permitted test-script correction loops have ended.

$$E2E\ Pass\ Rate_i=\frac{N_{passed,i}}{N_{total,i}}\times100\%$$

where $N_{total,i}$ is the number of applicable test cases specified in the JSON document for task $i$, and $N_{passed,i}$ is the number of those cases reported as passing in the final E2E result. Failed, unexecuted, or unresolved cases are not counted as passed. A missing test-case document or an unavailable final report is distinguished from a measured zero-pass result during data preparation (Section 4.2.5). Test-case expectations are not altered merely to produce a passing result.

**Defect Density**

Defect density uses confirmed defects linked to a feature-development task in Jira and available by the dataset's extraction cutoff. The code-size denominator is the final production-code change attributable to that task, measured from GitLab diffs rather than the size of the existing module.

$$Changed\ LOC_i=Added\ LOC_i+|Deleted\ LOC_i|$$

$$Defect\ Density_i=\frac{D_i}{Changed\ LOC_i/1000}$$

where $D_i$ is the number of distinct confirmed defects linked to task $i$. Added and deleted lines refer to the task's final production-code diff; test code and generated files are excluded from this denominator. The measure is therefore defects per thousand changed lines of production code, rather than defects per thousand lines in the entire module.

Valid tasks with a high defect density are retained, including cases with small changes. The raw defect count and changed LOC are kept alongside the calculated ratio to support interpretation. When changed LOC is zero, task-level defect density is undefined and is not calculated by division by zero; the task and any recorded defects remain in the dataset for other applicable measures.

**Supplementary E2E Test-Script Correction Loop Count**

A correction loop is counted when, following a failed E2E run, the agent diagnoses an error in its generated test script, changes the test code, and reruns the test. The initial E2E execution is not a correction loop, and fixes to business code are not counted as test-script correction loops. Both workflow conditions receive the instruction to allow no more than three loops: the baseline through prompts or project instructions and Trade-Harness through predefined workflow controls. The final report is returned when testing ends or the permitted limit is reached.

Loop counts are examined descriptively alongside final E2E outcomes when execution records are available. An observed breach of the instructed limit is recorded as a process deviation, but is not by itself evidence of a particular context or memory failure. Details of data sources, missing records, and comparative analysis are described in Sections 4.2.4 and 4.2.5.
