# Section 2.2 literature evidence map

Working structure: 2.2.1 problem and coordination; 2.2.2 existing approaches and empirical evidence; 2.2.3 gap and rationale for development lead time. These are source notes for drafting, not claims of Trade-Harness effectiveness. The additions below are recorded in `references/references.md`; already-listed sources are identified in the last section.

## 2.2.1 Problem: agent capability and coordination are different questions

- **Chou et al. (2026), _Developers as Managers of AI Agents_** — [original paper](https://arxiv.org/abs/2610.33588). Workplace shadowing of 11 professional developers for approximately 15 hours; 255 prompts and follow-up interviews. Prompt formulation plus checking AI responses accounted for an average 33.4% of *observed session time*. Direct evidence that developers perform supervision and coordination while using coding agents. It is neither an estimate of wasted time nor a comparison of native Claude Code with an orchestrated workflow. This supports describing a coordination burden without assuming an agent cannot plan or test.
- **Tang et al. (2026), _How Coding Agents Fail Their Users_** — [published paper](https://aclanthology.org/2026.emnlp-main.1011/). Observational analysis of 20,574 IDE/CLI coding-agent sessions in 1,639 repositories; identifies developer-visible misalignment in project reading, intent, rules, action boundaries and execution. The reported 91.49% requiring explicit user correction refers to **visible resolutions of identified misalignment episodes**, not to all agent sessions. Establishes possible developer correction work, not a measured delay or a proof that CLAUDE.md fails.
- **Otten et al. (2025), _Prompting in Practice_** — [original paper](https://arxiv.org/abs/2510.06000); already in bibliography. Survey of 91 engineers (72 active GenAI users); iterative multi-turn prompting was preferred and complex code generation/debugging presented challenges. Shows developer practices and reported challenges, not task-level lead-time effects or an evaluation of native Claude Code.
- **Song et al. (2024; arXiv v4 revised 2026), _The Impact of Generative AI on Collaborative Open-Source Software Development_** — [v4 original](https://arxiv.org/abs/2410.02091v4); already in bibliography. GitHub Copilot usage and OSS project data; authors report greater code contribution alongside an 8% increase in coordination time. Useful for the possibility that faster contribution can coexist with coordination overhead. This concerns collaboration among developers using Copilot, not developer-agent orchestration, and version-specific numbers must be cited from v4.

## 2.2.2 Existing approaches and evidence: compare settings and outcome measures

- **Peng et al. (2023), _The Impact of AI on Developer Productivity_** — [original paper](https://arxiv.org/abs/2302.06590); already in bibliography. Controlled task: implement a JavaScript HTTP server with/without GitHub Copilot; Copilot group finished 55.8% faster. This is evidence about that bounded task and code assistant, not enterprise issue lead time or a structured workflow.
- **Paradis et al. (2025), _How Much Does AI Impact Development Speed?_** — [conference paper / open preprint](https://arxiv.org/abs/2410.12944), [DOI](https://doi.org/10.1109/ICSE-SEIP66354.2025.00060). Randomized study of 96 Google engineers on one standardized enterprise-grade C++ task using three internal AI features. Authors estimate about 21% less time under their preferred adjusted model, with a wide interval crossing zero (reported p = .086 for that model); the unadjusted difference was statistically significant. Supports possible time gains under bounded conditions, not a general enterprise lead-time effect, nor a comparison of two agent workflows.
- **Becker et al. (2025), _Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity_** — [original paper](https://arxiv.org/abs/2507.09089). Randomized AI-allowed versus AI-disallowed assignment for 246 real repository issues completed by 16 experienced contributors. AI-allowed issues took an estimated 19% more *self-reported implementation time*, including pre- and post-PR-review effort; 74 screen recordings were coded for activity. Especially useful counterevidence against assuming net speedup. Their active implementation time is different from Jira status-to-status elapsed development lead time, and the contrast is AI availability versus no AI, not native CLI versus orchestration.
- **Chen et al. (2026), _Code with Me or for Me?_** — [original paper](https://arxiv.org/html/2507.08149v2), [conference DOI](https://doi.org/10.1145/3772318.3790850). Within-participant study of 20 students using GitHub Copilot and OpenHands on time-boxed tasks. For correctly completed tasks, mean active *user effort* was 25.1 minutes with Copilot versus 12.5 with OpenHands; including the agent's actions gave about 27.9 minutes in the agent condition. This directly illustrates why human active time and overall task time must be distinguished. Different tools with different capabilities, novices to the agent, and short tasks preclude treating it as evidence about Trade-Harness versus native Claude Code.
- **Xia et al. (2024), _Agentless_** — [original paper](https://arxiv.org/abs/2407.01489); already in bibliography. Explicit localization, repair and patch-validation phases achieved 96/300 resolved SWE-bench Lite issues at a reported mean model cost of $0.70 in the cited arXiv version. Demonstrates a viable structured alternative to autonomous execution in that benchmark; resolution and model cost are not developer coordination or delivery lead time. Check paper version if using later conference numbers.
- **Murphy-Hill et al. (2026), _Adoption and Impact of Command-Line AI Coding Agents_** — [original paper](https://arxiv.org/abs/2607.01418). Microsoft rollout of Claude Code and GitHub Copilot CLI; adopters were estimated to merge approximately 24% more PRs over the four-month window. Particularly relevant because it observes native agentic CLI tools in an organization. The outcome is PR throughput, not time per issue; observational attribution has limits; it does not compare native CLI with an additional orchestration workflow.

## 2.2.3 Research gap and why measure lead time

- **Forsgren et al. (2021), _The SPACE of Developer Productivity_** — [original article](https://doi.org/10.1145/3454122.3454124), [author-hosted record](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/). Conceptual measurement framework: productivity spans multiple dimensions; flow of a work item and its delays/handoffs are meaningful measures, but a single measure cannot represent total developer productivity. Use to justify measuring development-stage elapsed time *alongside* quality and computational cost, not to assert that lead time alone proves overall effectiveness.
- **Narrow gap supported by the set above:** The studies compare AI/no AI, different tool classes, or benchmark systems, or observe agentic CLI throughput and developer interaction. None of the studies **listed in this map** directly compares native Claude Code with an additional structured orchestration workflow on enterprise front-end tasks using the same model and task-level elapsed development-stage time. This is a conclusion about these sources, not a claim that no such research exists anywhere.
- **Operational boundary in this thesis:** Jira `In Progress` → `Development Complete` measures elapsed days in the developer-owned stage. It includes waiting within that stage and differs from active implementation time (Becker), active user effort (Chen), completed-task/PR count (Cui/Murphy-Hill), and DORA's commit-to-production change lead time. If the workflows differ, examine complexity, developer, assignment and waiting as alternative explanations. Do not attribute an observed difference to a particular Trade-Harness layer without direct process evidence.
- **Resulting RQ1:** How does delivery lead time differ between the structured agent orchestration workflow and the conventional prompt-based workflow? The direction is open. Native Claude Code can already inspect repositories, plan, run tools and test; the issue is whether an *additional arrangement* of those activities changes the observed outcome.

## Citation and drafting checks

- Use precise denominators: Tang's correction percentage is conditional on identified episodes with visible resolutions; Chou's 33.4% is within observed sessions.
- Avoid describing the Claude Code baseline as single-shot generation or incapable of tool use and testing.
- Distinguish causal experimental comparisons, observational association, benchmark results, and practitioner descriptions.
- Do not infer that coordination caused the Becker slowdown, or that Agentless reduced human lead time.
- Keep this bibliography map separate from the prose of 2.2 until paragraph-level claims are matched to the full papers.
