# Section 2.3 reference map

Working structure: **2.3.1** context and memory continuity as possible sources of output risk; **2.3.2** retrieval, selective memory, compaction and grounding, with empirical results; **2.3.3** evidence boundaries, evaluation and research gap. This is a drafting map, not a claim that Trade-Harness improves code quality. Here “quality” means only the study’s observed defect density and E2E pass rate; neither measure captures all properties of software.

The figures answer different questions under different benchmark and baseline conditions. |

Report task, model or agent, intervention, baseline, and metric before drawing a cross-study inference. Evidence of changes in API invocation, rediscovery effort, and issue resolution leaves open how a full enterprise front-end workflow differs on the two outcomes in RQ2.

## 2.3.3 Synthesis and study-specific measurement

- **Narrow synthesis:** The sources above indicate that useful context may be unavailable or poorly used, and show conditional gains from retrieval or structured memory in their respective benchmarks. The studies also include counterevidence: an indiscriminate reduction of dependency context can hurt (Hai), persistent context files need not improve success (Gloaguen), and handoff success gains differ by model (KC and Budathoki). This supports an empirical comparison, not a predicted positive effect.
- **Test evidence has its own boundary:** [Egashira et al. (2026)](empirical-evidence/egashira-et-al-2026-testsuitebench.md) finds that agent-generated suites can pass reference implementations yet miss requirement-targeted mutants. It concerns Rust/Go/C++ application test generation, not this study’s front-end E2E tests. It warrants cautious interpretation of *what a pass rate can establish*, especially if the agent also writes the tests; compare with actual test-case specifications and independent defect records.
- **Specific gap from this source set:** These papers evaluate long-input tasks, code completion, benchmark issue resolution, agent handoffs, or test-generation strength. In the sources mapped here, there is no direct estimate of how an additional structured orchestration workflow compares with native Claude Code for enterprise front-end tasks on **both** recorded defect density and E2E pass rate under the thesis’s protocol. This is a claim about the mapped studies, not an exhaustive claim about the field.
- **Measurement link:** Defect density uses recorded defect count divided by changed KLoC; inspect numerator, denominator, and task complexity because small changes can inflate the ratio. E2E pass rate depends on the specified cases and generated test scripts. Follow the study’s fixed test-case and correction-loop protocol when describing it, and do not conflate “tests pass” with absence of defects.
- **Inference boundary:** A quasi-experimental workflow comparison can estimate observed associations for these outcomes while accounting for developer/task differences. It cannot isolate memory, compaction, retrieval or individual Trade-Harness layers as causes without additional controlled comparisons and process evidence. The direction of the comparison remains open.
