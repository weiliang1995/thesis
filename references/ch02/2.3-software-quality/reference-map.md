# Section 2.3 reference map

Working structure: **2.3.1** context and memory continuity as possible sources of output risk; **2.3.2** retrieval, selective memory, compaction and grounding, with empirical results; **2.3.3** evidence boundaries, evaluation and research gap. This is a drafting map, not a claim that Trade-Harness improves code quality. Here “quality” means only the study’s observed defect density and E2E pass rate; neither measure captures all properties of software.

## 2.3.1 Problem: what can be lost, missed, or invented?

| Question / candidate claim | Source and evidence | Boundary for prose |
| --- | --- | --- |
| Context-window capacity differs from effective use of information. | [Liu et al. (2024), *Lost in the Middle*](../2.1-agent-engineering/context-engineering/liu-et-al-2024-lost-in-the-middle.md): long-input QA and retrieval; [Du et al. (2025)](problem/du-et-al-2025-context-length-alone.md): controlled tasks including code, even with perfect retrieval. | Results are not direct evidence that a Claude Code window limit produces front-end defects. Do not call every failure “context dilution”: information may be absent, hard to retrieve, or retrieved but poorly used. |
| Compaction may change which task facts remain available. | [Wang et al. (2026)](problem/wang-et-al-2026-context-compression-survey.md): method and failure-mode taxonomy; [Liu et al. (2026), *Context as a Tool*](https://aclanthology.org/2026.findings-acl.1032/): contrasts callable context management with static compression in a trained SWE agent. | The survey maps possible losses; it does not establish a loss rate for Claude Code. A different trained agent’s performance cannot be attributed to compaction alone. |
| Output can contain fabricated APIs or libraries. | [Twist et al. (2026)](problem/twist-et-al-2026-library-hallucinations.md): library-level hallucination study; [Eghbali and Pradel (2024)](https://arxiv.org/abs/2401.01701): project API grounding for Python completion and JavaScript test generation. | Hallucination is an observed code-output risk, not necessarily a *consequence* of a long context, faulty memory, or missing RAG. Do not merge these into one causal chain. |
| Interruption creates a selection and transfer problem: what to record for later work? | [KC and Budathoki (2026)](empirical-evidence/kc-budathoki-2026-handoff-debt.md): repository-only versus raw trace, summary and structured handoffs; [Shen et al. (2026)](empirical-evidence/shen-et-al-2026-subtask-level-memory.md): whole-issue versus subtask-level experience retrieval. | Handoff is continuation of a partial task; Shen’s memory is experience reused *across tasks*. They answer related but different questions. Neither establishes a universally optimal memory policy. |
| What native Claude Code already provides. | [Anthropic: memory and instruction documentation](https://code.claude.com/docs/en/memory) describes fresh session context, CLAUDE.md and auto memory; [context-window documentation](https://code.claude.com/docs/en/context-window) discusses compaction. | Product documentation establishes available capabilities, not failure prevalence or effectiveness. Check the version used in the study before writing historical claims. Avoid saying the baseline has “no memory” or cannot compact. |

**Drafting sequence:** Start with the information needed for a task across long interactions and sessions. Distinguish bounded context, placement/utilisation, compaction, and cross-session retention. Then introduce fabricated or inconsistent code as a *possible* output risk, without assuming each context issue caused it. The specific repository dependency question belongs in 2.3.2.

## 2.3.2 Existing approaches and empirical evidence

| Mechanism | Source / result in its own setting | Boundary and counterweight |
| --- | --- | --- |
| Repository retrieval and iterative grounding | [RepoCoder (Zhang et al., 2023)](../2.1-agent-engineering/context-engineering/zhang-et-al-2023-repocoder.md) iterates retrieval and completion; [De-Hallucinator (Eghbali and Pradel, 2024)](https://arxiv.org/abs/2401.01701) iteratively retrieves project-specific APIs and reports improvements in API prediction and JavaScript test repair. | Code completion, API prediction and generated tests are different outcomes from real issue resolution, defect density or E2E pass rate. Distinguish generic RAG from prediction-guided grounding. |
| Choosing dependency context | [Hai et al. (2025)](empirical-evidence/hai-et-al-2025-repoexec-context.md), 18 models on RepoExec: full dependency context performed best in the tested setting; smaller inputs could mislead. [Le-Anh et al. (2026)](empirical-evidence/le-anh-et-al-2026-cross-repository-graph-retrieval.md) extends retrieval to external library dependencies and reports benchmark gains. | More context can help when it contains needed dependencies; compare with Du/Liu on long-input utilisation. Cross-repository *library* retrieval is related to, but distinct from, multiple internal front-end repositories. |
| Selecting and structuring retained memory | [Shen et al. (2026)](empirical-evidence/shen-et-al-2026-subtask-level-memory.md) reports +4.7 percentage points mean Pass@1 over vanilla agents on SWE-bench Verified across the studied backbones; [KC and Budathoki (2026)](empirical-evidence/kc-budathoki-2026-handoff-debt.md) finds lower rediscovery effort with context-bearing handoffs, but solved-rate effects vary by model. | “Store everything” is not a tested general prescription. The handoff study's strongest consistent outcomes are effort/tokens, whereas Shen measures issue resolution. Neither measures this thesis's E2E or defect outcomes. |
| Explicit context maintenance | [*Context as a Tool* (Liu et al., 2026)](https://aclanthology.org/2026.findings-acl.1032/) reports 57.6% solved on SWE-bench Verified for a specially trained SWE-Compressor agent, relative to its stated ReAct and static-compression baselines. | Different model training and agent setup; cannot infer a benefit from simply adding a compaction step to Claude Code. |
| Negative or mixed evidence on persistent instructions | [Gloaguen et al. (2026, arXiv v3)](../2.1-agent-engineering/context-engineering/gloaguen-et-al-2026-evaluating-agents-md.md) reports that repository context files did not generally improve task success and increased average inference cost by over 20%. | Context files are one delivery format and the paper does not test all forms of selective memory, RAG, or Trade-Harness. Use as a check against claiming more persistent context necessarily helps. |

**Comparison rule:** Report task, model/agent, source of context, baseline, metric and direction before drawing a synthesis. Keep code-completion scores, SWE-bench resolved rate, handoff effort and front-end integration tests separate. A mechanism is a rationale to test, not a confirmed solution in this environment.

## 2.3.3 Synthesis and study-specific measurement

- **Narrow synthesis:** The sources above indicate that useful context may be unavailable or poorly used, and show conditional gains from retrieval or structured memory in their respective benchmarks. The studies also include counterevidence: an indiscriminate reduction of dependency context can hurt (Hai), persistent context files need not improve success (Gloaguen), and handoff success gains differ by model (KC and Budathoki). This supports an empirical comparison, not a predicted positive effect.
- **Test evidence has its own boundary:** [Egashira et al. (2026)](empirical-evidence/egashira-et-al-2026-testsuitebench.md) finds that agent-generated suites can pass reference implementations yet miss requirement-targeted mutants. It concerns Rust/Go/C++ application test generation, not this study’s front-end E2E tests. It warrants cautious interpretation of *what a pass rate can establish*, especially if the agent also writes the tests; compare with actual test-case specifications and independent defect records.
- **Specific gap from this source set:** These papers evaluate long-input tasks, code completion, benchmark issue resolution, agent handoffs, or test-generation strength. In the sources mapped here, there is no direct estimate of how an additional structured orchestration workflow compares with native Claude Code for enterprise front-end tasks on **both** recorded defect density and E2E pass rate under the thesis’s protocol. This is a claim about the mapped studies, not an exhaustive claim about the field.
- **Measurement link:** Defect density uses recorded defect count divided by changed KLoC; inspect numerator, denominator, and task complexity because small changes can inflate the ratio. E2E pass rate depends on the specified cases and generated test scripts. Follow the study’s fixed test-case and correction-loop protocol when describing it, and do not conflate “tests pass” with absence of defects.
- **Inference boundary:** A quasi-experimental workflow comparison can estimate observed associations for these outcomes while accounting for developer/task differences. It cannot isolate memory, compaction, retrieval or individual Trade-Harness layers as causes without additional controlled comparisons and process evidence. The direction of the comparison remains open.
